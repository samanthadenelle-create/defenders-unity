## Verdict vocabulary

- **ACTIVE / PROVEN:** the causal code path is present at HEAD and directly explains the defect.
- **IMPLEMENTED / STALE READY:** implementation is on HEAD; the ticket remained in Ready because its
  status/verification bookkeeping did not follow the code.
- **PARTIAL:** some implementation exists, but a named acceptance condition is still false or unproved.
- **EVIDENCE GAP:** the symptom is real, but available data cannot distinguish the remaining causes.
- **CONFOUNDED / PROVEN:** the measurement is real, but retained telemetry proves simultaneous
  uncontrolled factors, so it cannot identify one dominant runtime cause.
- **SPEC / RULING / EXTERNAL:** not a defect RCA; it requires design, owner, platform, or linguistic work.
- **RETRACTED:** the ticket's proposed root was falsified by later evidence.

### WO-1095 — raid watchdog fires after long staging

This cause is data- and source-proven. The persistent break log records raid-scene entry at realtime
`1848.566162` (`2026-09-09T17:15:42.851Z`) and watchdog failure at `2073.543457`
(`17:19:27.828Z`): a delta of `224.977295` seconds, matching the watchdog's `180 + 45` second bound.
The contemporaneous 1232x699 capture
`C:\Users\Elden\AppData\Local\Temp\codex-clipboard-FJGtex.png` (SHA-256
`8BCDE7BADAE1C1D4234A048C469230BB9E350EF596F0AF4A8EC6850CE55F1B27`) shows `2:46` remaining,
so only 14 seconds of the actual 180-second raid clock had elapsed.

`RaidScoring.Update` returns before adding `Time.deltaTime` until engagement, intentionally making
staging free. `RaidDeployController.RaidEndWatchdog` instead increments `aliveFor` with unscaled delta
from scene startup and compares that scene-age value with `clock + 45`, without consulting
`RaidScoring.Engaged` or `RaidScoring.ElapsedSeconds`. The player spent about 211 seconds staging and
14 seconds engaged; the watchdog consequently fired at 225 seconds of scene age with 166 seconds of
valid raid time still displayed. Blame traces the engagement-gated clock to `d6511b8e52` and the older
scene-age watchdog to `5bc5025f5b`. This is a cross-change invariant regression: the real clock and its
watchdog no longer measure the same interval.

### WO-1092 — one valid Orc bundle is trapped behind an abandoned cache lock

The verifier's arithmetic is reproducible: `38,549,656 - 19,398,472 = 19,151,184` bytes, exactly
equal to the five cache `__data` files present at completion (`11,269,635 + 6,216,707 + 1,096,169 +
482,203 + 86,470`). All 24 download chunks reported success, yet the same-key remeasurement still
required 19,398,472 bytes. This proves the verdict is sound, the 77,346,600 progress numerator is
display-only shared-bundle double counting, and approximately half the required bytes did not become
usable cache entries.

The original build catalog and quarantined cache both survive, allowing the missing entry to be
reconstructed without changing runtime code. Parsing the build's binary catalog yields 97 distinct
bundle requests. Against the post-failure cache, 89 are present; seven of the eight absent requests
are local player bundles and contribute zero download bytes. The sole absent remote request is:

- primary key `enemy_models_assets_enemyfam-orc_2220522384eb58b0db363f6c6e1b47ab.bundle`;
- URL under the build's `StandaloneWindows64` R2 path;
- cache bundle name `912fa7abd447ca13619697b1fce844c6`;
- valid non-zero hash `2220522384eb58b0db363f6c6e1b47ab`;
- catalog size **19,398,472 bytes** and CRC `4262033540`.

That bundle-name directory is not absent. Its current-hash subdirectory was created at
2026-09-08 14:51:27 local and contains only a zero-byte `__lock`; it has no `__data` or `__info`.
The preceding hash `3c9df7ea9a3c1566f0cde489711dfec6` remains complete at 19,400,698 bytes. This is neither an
invalid-hash defect nor an ordinary eviction: Unity began the current cache transaction, abandoned
it before commit, retained the lock, and preserved the old version. The machine also had 159 GB free
when audited, and no cache-repair trace ran in the captured session.

The progress total identifies the behavioral consequence exactly:
`19,151,184 + (3 x 19,398,472) = 77,346,600`. The five successfully committed bundles were counted
once, while three separate key chunks fetched the shared Orc bundle, each handle reported success,
and every fetch remained memory-only because the cache transaction never finalized. Therefore the
definitive RCA is an **abandoned current-version cache lock / incomplete cache commit**, amplified by
chunking addresses instead of unique bundles. A targeted recovery may remove or repair that exact
stale version transaction before one bounded retry; relaxing the verifier would conceal the defect.

### Raid ballista stands on its edge and is enormous

This cause is source-proven. The easy raid config reports central art `tower_siege_tower` in the live
log. `RaidBaseGenerator.PlaceSpire` treats every central building as a monument: it applies

`PlaceSpire` does not. `RaidBaseDresser.MapCatalogArt` also maps ids containing `siege` directly to
`Ballista`, preserving the mismatch rather than selecting architectural spire art.
