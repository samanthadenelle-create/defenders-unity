# Command Center — Reference

What this document is: a complete, source-verified map of the admin/ops console ("Command
Center") as it exists in this repo right now. Everything below was read directly from the live
code (`api/admin/console.js`, `api/admin/stats.js`, `api/admin/ops.js`, `api/admin/promo-bind.js`,
`api/admin/db.js`, `api/_lib/tunable-manifest.js`), not from work-order titles or memory — where a
work order's name suggested a feature that isn't actually live, that's called out explicitly
rather than assumed.

---

## How it's built

- **One file, one page, no framework.** `api/admin/console.js` is a Vercel serverless function
  (plain Node.js, `module.exports = async (req, res) => ...`) that returns a single self-contained
  HTML document — no build step, no CDN, no webfonts, no external images. This was a deliberate
  choice (WO-1244): the owner needs to use this one-handed on a phone, often in the middle of an
  incident, not at a desk.
- **7-bit ASCII, enforced at serve time.** The manifest JSON that drives the Balance tab is
  scanned byte-by-byte at module load; any character above 126 or below 32 throws before the page
  can ever serve. `test/command-center.test.js` pins this.
- **Two keys, two endpoints, no exceptions.**
  - **Read**: every GET to `/api/admin/stats` or `/api/admin/db` requires header
    `X-Admin-Key` matching the `ADMIN_DASH_KEY` environment variable (constant-time compare).
  - **Write**: every POST to `/api/admin/ops` or `/api/admin/promo-bind` requires BOTH
    `X-Admin-Key` (the read key) AND `X-Admin-Ops-Key` matching `ADMIN_OPS_KEY`.
  - The page itself (`console.js`'s served HTML) is **not** key-gated — it can't be, because a
    plain browser navigation can't carry a custom header, and putting the key in the URL would
    leak it into browser history, referrers, and every log line on the way. So the *shell* is
    public (and marked `noindex, nofollow`) and carries zero data; it only becomes useful once a
    key is typed into the in-page gate.
  - **Neither key is ever persisted.** They live in two JavaScript variables for the life of the
    browser tab — never `localStorage`, `sessionStorage`, a cookie, or a URL parameter. Reloading
    the page asks again, by design.
- **Colour is never the signal.** The owner is red/green colourblind. Every state on this page is
  spelled out as a word — `CLOSED`, `open`, `ALERT`, `ACTIVE`, `DISABLED`, `verified`,
  `unverified`, `MISSING`, `COULD NOT READ` — and the one accent colour is decoration only.
- **A failed read is never rendered as zero.** This is a repeated, explicit design rule across the
  whole page: if a query fails, the area that depends on it prints "COULD NOT READ" (or the
  specific reason) and shows no figure at all, rather than defaulting to 0 or an empty table. The
  code comments call this out as a "confident lie" the project has been burned by before.
- **No PII, ever.** No wallet address, email, or real player name is rendered anywhere on this
  page. Player identifiers arrive already masked from the backend; promo-code wallet bindings
  arrive as a plain boolean ("bound" / "not bound"); bug reports show "verified" / "unverified"
  identity, never the underlying account.

### Where the code lives

| Piece | File |
|---|---|
| The console page itself (HTML/CSS/JS, all inline) | `api/admin/console.js` |
| Read-only data endpoint (all the `view=` queries the console fetches) | `api/admin/stats.js` |
| Write endpoint (the 7 operator actions) | `api/admin/ops.js` |
| Promo-code-to-Google-player binding (separate write endpoint, separate key requirement) | `api/admin/promo-bind.js` |
| Lower-level raw-DB diagnostic endpoint (broader than the console needs; console only calls its `view=ads`) | `api/admin/db.js` |
| The Balance tab's knob catalog, generated from the game's own tunables registry | `api/_lib/tunable-manifest.js` (spine generated by `tools/gen-tunable-manifest.mjs` from `DeNelle.Core.Ops.RemoteTunables.Registry` in the Unity project) |
| Shared ops helpers (kill-switch state, promo tables, etc.) | `api/_lib/ops.js` |

## The landing structure

On open, the console shows a **primary nav** with three items: **Decisions** (opens by default),
**Balance**, and a **More tools** disclosure button. Tapping "More tools" reveals a second row of
seven older, more granular tabs: **Players, Toggles, Money, Player issues, Promos, SKUs,
Tickets**. This two-tier layout (WO-1281) was a deliberate reorganization — the seven older tabs
still exist and do exactly what they always did; the change was to put a synthesized "what do I
need to decide today" view in front of them rather than removing anything.

A top bar lets the operator pick a reporting window (7 / 30 / 90 days, default 30) and manually
refresh. Every tab re-fetches on window change.

## Tab: Decisions (the default landing tab)

Backed by `GET /api/admin/stats?view=command&days=N`. This is the newest, most synthesized part of
the console (WO-1281) — four collapsible areas, phrased as business questions, one open at a time
so the page stays scannable on a phone. Opening one auto-closes whatever else was open.

### 1. Sales — "What is selling?"
- Headline tiles: settled revenue for 30 days / 7 days / today, each with unit count and a
  trend word (vs. the prior equivalent window) — or, if nothing has ever sold, an explicit
  "NO PURCHASE HAS EVER SETTLED" state instead of a fabricated zero.
- **Ad income sits directly under the sales tiles, unexpanded** (WO-1796) — this was a direct
  response to the owner's own words, quoted in the code: *"noone is ever buying a pack and I cant
  figure out how to see if ads are making anything."* Ad revenue is printed to **4 decimal
  places** (`usd4()`), not the usual 2, because real per-day ad revenue on this game has been as
  small as $0.02–$0.19 for a whole measured month — rounding to 2dp would show "$0.00" and be
  indistinguishable from "earned nothing."
- Expanded detail includes: window-over-window trend table, all-time settled total and buyer
  count, full ad-revenue breakdown (by network / by day / by placement, plus rewarded-ad
  completions by provider), first-time-vs-repeat buyer split, the "quote to settle" funnel (wallet
  prompts opened vs. actually paid vs. expired unpaid), a live client/server purchase-disagreement
  count (with a pointer to the Money tab to review it), the full sellable-SKU roster with per-SKU
  sales, and an explicit **"Pushing or featuring a SKU" state marked NOT INSTRUMENTED** — the code
  deliberately does not offer a "feature this SKU" button because no shipped client reads such a
  flag yet, and a button that changes a DB column nothing reads would look like it worked while
  doing nothing.

### 2. Retention — "Do players come back, and for how long?"
- Headline: next-day return rate, 7-day-still-here rate, and active-player count for the window
  vs. trend.
- Expanded detail: median/mean/90th-percentile session length (explicitly labeled `MEASURED` or
  `ESTIMATE` depending on instrumentation depth), full D1/D7/D30 return-rate table with a
  "usable" / "too few to trust" / "no cohort has aged this far" confidence word per row, a
  new-vs-returning player growth comparison, and a three-way churn breakdown: **one session only**,
  **tried and left**, **returned but stalled** — each with its own precise definition printed on
  the page (not just a number) plus a "where they stopped" table of last-known actions before
  players went quiet for 7+ days. A closing note explicitly states what counts as "playing" and
  what doesn't, sourced from the backend, not hardcoded here.

### 3. Progression — "Are returning players levelling up?"
- Headline: median hero level, percent of saves that got past level 1, median best wave reached.
- Expanded detail: coverage stats (how many saves even carry a hero-level field — a real,
  named gap if telemetry coverage is incomplete), a hero-level distribution table, wave-clear and
  structure-count stats, and an explicit **"What this area cannot answer"** list — named gaps
  (missing instruments), never papered over with an adjacent number.

### 4. Diagnostics — "Is the telemetry itself healthy?"
- Headline: percent of events that arrive with an identified player vs. anonymous, and raw
  anonymous-event count.
- Expanded detail: excluded-ID count (operator/test traffic filtering), oldest/newest event
  timestamps, and a full breakdown of every distinct event name the game is actually sending, with
  count / distinct-player count / most recent timestamp per event — useful for spotting a dead or
  newly-broken telemetry call without reading server logs.

Any of the four areas can independently show **"COULD NOT READ"** if its backing query failed,
without blanking the rest of the page — each query is fetched and evaluated separately.

## Tab: Balance (WO-1328 — "the balance editor")

Origin, quoted directly from the code comment: owner, 2026-09-02 — *"should be in command center
so you dont need to be a rocket scientist... they can have a simple UI that drives a json,"*
in the same breath as *"i have been screaming this for months."*

This tab lets the owner override specific gameplay-tuning numbers on the **live, already-shipped**
build without a new release — a `client_tunables` table the game polls (roughly a 40-second
pickup time on a running client). It is driven entirely by a generated manifest
(`api/_lib/tunable-manifest.js`, built from the Unity project's own `RemoteTunables.Registry`),
so **the console can never show a knob the build doesn't have, and can never hide one the build
does have** — adding a lever is purely a data change on the Unity side plus a manifest
regeneration, never a UI edit here.

**Four areas**, each a named section with its own knobs:
- **Skills** — ability strength and cooldown values.
- **Tiers** — per-level/per-rank scaling for skills or structures.
- **Spells** — cast behavior (damage, healing, drain) and which visual effect a spell uses.
- **Misc** — everything else that ships as a tunable number (a mixed bucket; two of its knobs are
  read only at game startup and need a relaunch to take effect, and each such knob says so on its
  own card).

**Every knob card shows, in words, never in colour:**
- The current effective value.
- The value the *installed build itself* ships with (its compiled-in default).
- Either **"OVERRIDDEN"** (an override row exists in the DB) or **"Shipped default — nothing is
  overriding it"**.

**Three knob shapes**, each with its own control set:
1. **Numeric** (most knobs) — a stepper (+/−) and a direct-entry field, a "Save this value" button
   (writes `tunable.set`), and a "Reset to shipped" button (writes `tunable.clear` — this
   **deletes** the override row so the game falls back to its own compiled default; the page is
   explicit and repeated that this is *not* the same as saving 0).
2. **Boolean** — ON / OFF buttons plus a Reset.
3. **Named option** (currently only the VFX picker, WO-1348) — a dropdown of options the manifest
   already knows are shipped in the build (so a pick can never reference art the build doesn't
   have — a direct lesson from a past incident where unshipped Addressable content failed with
   *no error on screen at all*, per CLAUDE.md §16). Saving here takes effect on the *next town
   load*, not immediately, and the page's own confirm dialog says so before writing.

Every write is confirmed with a `window.confirm()` dialog that restates exactly what will change
and (for numeric/pick saves) the propagation delay, before the request is sent.

If the manifest itself doesn't match the live build (a lever the game registry no longer has, or
vice versa), the page prints an explicit `MANIFEST DOES NOT MATCH THE BUILD` alert rather than
silently showing a stale or broken control.

## Tab: Players ("Live player pulse")

Backed by `GET /api/admin/stats?view=overview&days=N`. The general telemetry/DAU dashboard:
- A hero tile: active players in the last 24 hours, refreshed on load.
- 7-day and 30-day unique active counts, and today's session count.
- A daily-active-players bar chart (one bar per UTC day, hover/focus for the exact count and
  session count that day).
- Telemetry health: percent of sessions that carry an identified player vs. anonymous, raw
  anonymous session count, and lifetime total event count.
- A "new players per day" table (first-ever identified event per player, grouped by day), each row
  cross-referenced against that day's active-player and session totals.

## Tab: Toggles (kill switches + operator write history)

Backed by `GET /api/admin/stats?view=ops&days=N` (read) and `POST /api/admin/ops` with actions
`maintenance.seal` / `maintenance.open` (write).

- If the whole server is sealed, a top-level alert banner says so, and the note explicitly states
  every other area is closed too regardless of its own individual row.
- One row per maintenance area (e.g., a specific game system that can be closed independently).
  Each row shows: current state word (open/closed), when it was last flipped and by whom, an
  operator note if any, and the exact banner text players see if it's currently sealed.
- **Sealing an area** requires typing the banner message first — the "Seal" button is refused
  client-side (`MESSAGE_REQUIRED_TO_SEAL`) if the message field is empty, because a banner with
  nothing to say is worse than no banner. A confirm dialog states enforcement takes effect
  server-side in about 5 seconds and the player-facing banner in about 40 seconds.
- **Re-opening an area** also clears its banner text; confirmed before sending.
- Each area row can expand to show the actual matching server-side refusal records ("gate issues")
  for that window — timestamp, refusal kind, a salted player fingerprint (never a wallet), a
  correlation reference, and the request path.
- A separate "Recent operator writes" table logs every write this console has ever made — action,
  target, outcome, and operator attribution — so there's an audit trail independent of Git history.

## Tab: Money

Backed by `GET /api/admin/stats?view=purchases&days=N`. Purely about reconciling what the game
*client* reported happened against what the *server* actually settled — deliberately never
blended into one number, because the whole point is to expose disagreement between the two.

- **Top alert**: any purchase the client reported as completed with **no matching server-side
  entitlement** — a real, first-priority financial anomaly (a customer may believe they paid and
  received nothing, or paid twice). Each row can be **acknowledged** (`purchase.alert_acknowledge`)
  — explicitly labeled "no action" in the UI; acknowledging is a note-taking action only, it does
  **not** grant, refund, or otherwise touch money. A confirm dialog states this plainly before
  sending.
- Client-reported vs. server-settled counts side by side (never merged), plus a count of
  server-settled purchases the client never even reported (meaning normal client-side analytics
  *understates* real sales).
- All-time and windowed settled-purchase totals (count + USD).
- The same quote-to-settle funnel shown on the Decisions/Sales tab, repeated here in its original,
  more raw table form.
- A "not marked fulfilled" list — settlements whose fulfillment flag never got set. The page states
  explicitly that **this console cannot re-grant anything** — that would be a write against the
  money tables, and there is no button for it here on purpose.

## Tab: Player issues

Backed by `GET /api/admin/stats?view=ops&days=N` (the `reports` field), reading from the
`bug_reports` table. Read-only — no actions here.

Table columns: report id, timestamp, description, the in-game route/screen it was filed from, app
version, platform, identity state (`verified` / `unverified` — never an actual identity), and
whether a screenshot was attached. The page notes explicitly that `bug_reports` has, on some
deployments, never received a single row — so an empty list here is *not* proof the reporting
channel is actually working; it could just as easily be broken.

## Tab: Promos

Backed by `GET /api/admin/stats?view=ops&days=N` (read) and two separate write paths:
`POST /api/admin/ops` action `promo.create` / `promo.set_active`, and the entirely separate
endpoint `POST /api/admin/promo-bind` for binding a code to a specific Google-signed-in player.

**"Author a promo code" form** — creates a new code with:
- The code string itself (stored uppercase, since the game client uppercases on redemption).
- A reward: **either** a pack SKU **or** crystals/coins, never both — the form refuses both being
  set, because if both were allowed the SKU would silently win and the crystal/coin values would
  be dead data with no indication why.
- The SKU field is a dropdown sourced live from the same pack catalog the SKUs tab reads (WO-1599,
  a direct answer to an owner request to stop having to type SKU strings by hand) — but a "Type it
  instead" toggle always remains available, because a pack authored straight into the database
  (not yet in the shipped catalog file) still needs to be mintable. If the catalog itself fails to
  read, the dropdown disables itself and the typed field becomes the only option — the page never
  leaves the operator with two dead inputs.
- Optional: a player-facing message, max redemption count (blank = unlimited), per-player limit
  (blank = none), and an expiry timestamp (blank = never).
- Optional **discount window** (WO-1833) — a percent-off (0–70%) shared by every redeemer of that
  code, with its own start/end time, entirely separate from the site-wide sale knob described
  below. A percent requires an end time. Times are entered in the browser's local zone and
  converted to UTC before sending.
- **Wallet-address binding is deliberately NOT exposed in this form** (WO-1244) — authoring one
  here would mean typing and later displaying a wallet address, which this console refuses to ever
  render. That path stays a direct SQL / operator-CLI job.

**"Bind code to Google player" card** — a separate, narrower form: Google email + an *existing*
active code. This does not create or grant anything; it only attaches an existing code to a
specific player found by email lookup (requires that lookup to be enabled server-side; only a
fingerprint of the email is stored, never the email itself). A rich set of specific refusal reasons
is surfaced in plain language (no match, ambiguous match, code not found/inactive, already bound
elsewhere, etc.) rather than a generic error.

**Codes table** — every promo code: code, state (ACTIVE/etc.), what it grants (pack or
crystals+coins), redemption count vs. cap, expiry, whether it's privately bound to one player, and
an Enable/Disable toggle (`promo.set_active`) per row, each confirmed before sending.

> Note on the site-wide discount vs. per-code discount: the codebase and prior work orders
> (WO-1799 "storewide sale knob") describe **two separate discount mechanisms** — a per-wallet
> single-use coupon (via a promo code's own discount window, described above) and a
> site-wide sale percentage. The site-wide knob's live storage/read path was not traced further in
> this pass; if you need its exact current mechanism, check `api/_lib/store-sale.js` directly
> (not fully read for this document — flagged rather than guessed at).

## Tab: SKUs (WO-1532 — full catalog + sellability audit)

Backed by `GET /api/admin/stats?view=skus` (deliberately has **no** time-window parameter — a
catalog isn't a time-series). Entirely read-only.

Origin, quoted directly: owner, 2026-09-06 — *"can we add a list in command center of All SKU's and
contents."*

- Summary tiles: total pack count, how many are visible on the shelf (`storeVisible`), how many
  are actually **sellable** (anchored on a price ladder *and* visible), and how many have a "parity
  gap" (authored but cannot actually be sold as written).
- **Full table, one row per pack**: SKU id, display name/tagline, tier, storefront section, shelf
  visibility, price in every supported currency (USD/USDC/SOL/SKR), whether a USD price-ladder
  anchor exists server-side (**without this row, the wallet purchase rail cannot sell the pack no
  matter how the storefront card looks** — the page states this is a real failure mode that has
  shipped before), whether a Google Play product-type mapping exists (**without this, Google Play
  billing refuses the SKU outright**), an overall sellable yes/no with a plain-language reason, and
  the pack's actual granted contents (economy resources, cosmetics, convenience items) nested
  underneath.
- Any pack with a parity gap gets an explicit `MISSING` row spelling out exactly which rail it's
  missing from.
- A reverse-direction check: **"Priced, but not a pack"** — any SKU the payment rails know a price
  for that isn't a row in `packs.json` at all (this can be legitimate — e.g. Monthly Ledger cards
  authored in a separate `battle_monthly.json`, or a mainnet proof-of-rail canary SKU that was
  never meant to be a real sale — but it's always named, never silently dropped from the list).
- This tab makes **no writes at all** — it exists purely to answer "what can players actually buy
  right now, and where would that silently break."

## Tab: Tickets (Board)

A static informational card, not a live feed. Explains that there are **two deliberately separate
ticket systems**:
1. **Dev work** — `WorkOrders/*.md` in this repo, rendered into `BOARD.html` at the repo root by
   `python tools/board_build.py`. The repo is the source of truth; the board is a derived,
   local-file view and is never itself served over the internet.
2. **Player issues** — the "Player issues" tab described above, reading `bug_reports`. The page
   explicitly warns not to fold these into `BOARD.html`, since that file is regenerated from the
   repo on every run and anything hand-written into it would be silently overwritten.

## A lower-level surface this reference should flag: `api/admin/db.js`

The console's own code only ever calls **one** view on this endpoint (`view=ads`, for the ad
revenue numbers shown on the Sales tab). But `api/admin/db.js` itself implements many more views
that no console tab currently surfaces: `overview`, `players`, `metrics`, `ads`, `traces`,
`purchases`, `bugreports`, `bugreport`, `authrejects`, `events`, `funnel`. This looks like a
broader, lower-level raw-diagnostic API — likely intended for direct operator/CLI queries during
an incident rather than console-tab consumption. **Not fully investigated for this document** —
if you need to know what each of those views returns, read `api/admin/db.js` directly.

Similarly, `api/admin/stats.js` implements several `view=` values the current console **never
fetches**: `retention`, `funnel`, `economy`, `playtime`, `active`, `monetization`, `stability`,
`players` (this last name collides with, but is distinct from, the `overview` view the Players tab
actually uses). These may be superseded by the newer `command` view (which appears to synthesize
several of them), or may be dead/legacy code paths, or may be used by some other consumer outside
this repo. **This was not resolved for this document — flagged rather than guessed.** If any of
these turn out to be load-bearing for something, that should be confirmed at source before relying
on this document's silence about them as "doesn't exist."
