# WORK ORDER 1857 — Codebase-wide sweep: every hardcoded player-facing string routes through localization

**Status:** READY TO IMPLEMENT

**Minted:** 2026-09-17, by the CLI lead, from the owner's own words, stated as a standing law: *"this
is supposed to be a steadfast rule for all development. Anything that has text needs to go through
local so we can be put in all the languages that's a law that we have."*

**Owner routing directive:** assign to LOW-tier (Haiku) agents on tonight's overnight cycle. This is
monotonous find-and-wire work — locating literal strings and pointing them at existing or new locale
keys — not judgment work, and does not need heavy-model oversight per lane. The CLI lead still gates
and commits every lane's output as usual; only the per-string implementation work is low-tier.

## The concrete violation that surfaced this

`Assets/_Modules/HUD/Kit/HudKitController.cs` — the gear-dock slide-out tab set, `AddDockTab` calls at
`:5550-5553`, has shipped raw hardcoded English literals with ZERO locale resolution since it was
built (WO-439/WO-1399 history): `"Chat"`, `"Leaderboard"`, `"Music"`, `"Settings"`, and (read the file
for the remaining two rows — `"Realm"`/`"Pause"` per the class doc comment at `:1204`). `AddDockTab`
itself (`:5737`) passes `label` straight into `ElarionUiKit.BuildObsidianButton` with no
`LocalizedText`/`LocalText.Get` call anywhere in the path. This was caught only because the owner
noticed a NEW button (WO-1856's safety-net Settings door) doing the same thing and asked directly
whether it was localized — it was not, until fixed in that ticket by reusing the existing
`"settings.title"` key (already present and translated in all 10 supported locale JSON files).

**This is not an isolated miss.** If one of the most-shipped, most-visible HUD surfaces in the game
has six hardcoded labels, the sweep needs to cover the whole `Assets/_Modules/` tree, not just this
file.

## Scope

1. **Find every hardcoded player-facing string.** A tool already exists that does most of this
   automatically: `docs/localization/manifest.json`, generated by
   `tools/localization/build-string-manifest.ps1` — its own header says `"mode":"report-only"` and it
   already scans `runtimeCSharp` for `Assets/_Modules/**/*.cs` (Editor/Test/Regression excluded) and
   flags `literalCandidate` entries (5537 counted as of the last generation this session). **Re-run
   this tool first** rather than re-inventing string discovery, and confirm its candidate list still
   actually contains the `AddDockTab` labels above (if it doesn't, the tool itself has a gap that
   needs naming before trusting its output for the rest of the sweep).
2. **Triage each literal candidate** into:
   - A genuine player-facing string with no locale key today → needs one minted (or an existing key
     reused, per the localization-law memory: never a synonym key for a concept that already has one
     — grep the canonical JSON for a close match before minting).
   - A string that is data/identity, not copy (an enum name, a debug/editor-only label, a `FlowTrace`
     diagnostic message, an internal dictionary key) → correctly excluded, leave alone. Do not
     "localize" internal identifiers — CLAUDE.md and the existing `HudStrings.cs`/`SettingsText.cs`
     pattern already draw this line (icon identities stay stable English data keys; only the
     *displayed* text localizes).
   - A false positive from the scan tool → note it so the tool's own exclusion list can improve.
3. **Wire each genuine hit** using the established pattern for its owning assembly/area (see
   `Assets/_Modules/Core/UI/HudStrings.cs` and `Assets/_Modules/Settings/SettingsText.cs` for the two
   house patterns already in use — const-key-plus-Get()/Format() for HUD chip/face copy,
   readonly-`LocalizedText`-fields for screen-owned copy. Match whichever pattern the owning file's
   neighbors already use; do not introduce a third pattern).
4. **Add the English value** to `Assets/Resources/Data/Canonical/en.json` AND
   `Assets/StreamingAssets/Data/Canonical/en.json` (both copies must match — this is exactly the class
   of bug WO-1857's own trigger ticket, the "Defense Reports" fix, hit earlier today) AND
   `Assets/Localization/Tables/GameStrings_en.asset` (the Unity Localization package's own generated
   table — also proven today to be a THIRD copy that silently drifts if only the JSON is touched;
   `LocaleParityRegression` will catch a mismatch between the JSON and this asset, so treat a green
   `REGRESSION_OK` as the actual proof, not "I edited the JSON").
5. **For non-English locales**, a professional-quality translation is not required from the agent —
   a competent placeholder translation (matching the tone/register of neighboring rows in that
   locale's file) is acceptable for this sweep; flag anything that reads awkward for a follow-up
   linguistic pass rather than blocking the sweep on it. The AddDockTab six labels specifically
   ("Chat"/"Leaderboard"/"Music"/"Settings"/"Realm"/"Pause") are short single words/phrases with
   existing close analogs elsewhere in most locale files — reuse the closest existing translation of
   the same concept where one exists (e.g. `"settings.title"` already gives you "Settings" in all 10).

## Non-scope

- No changes to which strings SHOULD exist or what they say in English — this is a routing/plumbing
  sweep, not a copy rewrite. If a string's English wording looks wrong or stale while you're there,
  flag it in the hand-back; do not rewrite copy as a drive-by.
- No changes to `LocalText.cs`/`LocalizedText`/the resolution machinery itself — it already works
  (proven by every other correctly-wired string in the game). This ticket is about coverage, not the
  plumbing's design.
- Do not touch Editor-only, Test-only, or Regression-only files' strings — the manifest tool already
  excludes these on purpose (they are developer-facing, not player-facing).

## Acceptance criteria

- [ ] `docs/localization/manifest.json` re-generated; its `literalCandidate` count and the specific
      `AddDockTab` hits (if present) are cited in the hand-back.
- [ ] Every genuine hit from that scan is either wired to a locale key (new or reused) or explicitly
      justified as correctly-excluded data/identity, itemized in the hand-back — not silently skipped.
- [ ] Every new/changed key exists, with matching values, in: `Assets/Resources/Data/Canonical/en.json`,
      `Assets/StreamingAssets/Data/Canonical/en.json`, `Assets/Localization/Tables/GameStrings_en.asset`,
      and all 9 other locale JSON files (placeholder-quality translation acceptable per §5 above).
- [ ] `LocaleParityRegression` passes clean (this is the actual proof the three English copies match).
- [ ] `node`/C# gate: brace balance + NUL scan on every file touched; Unity compile gate +
      DataRegression (full `REGRESSION_OK <n>/<n>`) on the combined tree.
- [ ] The six `AddDockTab` labels specifically are fixed as a minimum floor for this ticket, even if
      the broader sweep has to continue in a follow-up ticket for scale reasons.

## Rollback

Purely additive locale-key/value changes plus call-site swaps from literal to key lookup; reverting is
a straight `git revert` of the lane's commit(s), no schema/save implications.

## Copy rules

No investment/jargon language (not applicable here beyond the standing rule) — the standing rule this
whole ticket exists to enforce: **every player-facing string routes through localization, no
exceptions, ever.**
