## ⚠ RCA — the "Current state" section below was WRONG (corrected at source 2026-09-17)

Its author read `DungeonHud.uxml` / `.uss`. **That path is DEAD at runtime.**
`DungeonHudController.HideLegacyUxmlHud` (`:212-231`) hides the `dungeon-hud-root` sub-tree on every
enable, and `Assets/Editor/Regression/ComposedDungeonRunRegression.cs:327` FAILS the suite if a UXML
oil meter is resurrected (UXML does not render in player builds — CLAUDE.md §8). So the caption /
time label / low-oil pill the section describes **were never on screen**, and the 11-12px font sizes
in `DungeonHud.uss` are a real font-floor violation in a file no player sees. Those two files were
deliberately NOT edited.

**The two proven causes, both in `DungeonHudController.cs`:**

1. **The shipped card had NO TEXT AT ALL.** `BuildKitHud` built an obsidian card + an ObsidianBar
   (`withValue: false`) + a pulsing ember, and nothing else — no caption naming the gauge, no
   burn-time readout, no low-oil pill. `DungeonHudVM.TimeLabel` ("Light: 1m 12s") already existed
   and the View simply never read it. A comment at the old `:177-178` claimed the countdown text was
   "deliberately" omitted; the owner's acceptance ruling ("make the duration legible") outranks an
   unattributed code comment, and that also left the low/critical state carried by **hue alone**,
   against the file header's own COLOURBLIND LAW.
2. **No safe-area inset.** The card was pinned at a raw `(24,-24)` from the screen corner.
   `SafeAreaInset` (WO-868) exists for exactly this — screen-anchored HUD chrome — and top-left is
   where a landscape phone's cutout / rounded corner sits. The device was clipping the panel.

**No overlapping HUD element was found** — `DungeonToastView` is top-CENTRE at sortingOrder 720,
`ObjectiveStripUi` is bottom-centre and village-FTUE-only, no `dg_*` scene bakes a HUD canvas, and
`HudKitController` is not `DontDestroyOnLoad`. "Hidden by the hud" was the panel reading as
anonymous chrome plus the device clip, not a z-order collision.

**Observation, not changed (out of scope):** the canvas uses a PORTRAIT `referenceResolution`
(1080x1920) in a landscape game. The `matchWidthOrHeight: 0.5f` scale math lands near 1.0-1.1, so it
is not the cause.

500-line diff per file. Each insert replicates its anchor line's own EOL and indent bytes.

**Verified:** all 20 files parse; 502 keys each (500 + 2); identical key SET across all 10
locales (no missing/extra); every `Resources` file byte-identical to its `StreamingAssets`
mirror; newline profile preserved exactly (en 506->508 CRLF / 0 bare-LF, others 503->505 CRLF /
3 bare-LF unchanged). `LOCALE_PARITY OK`.

**Finding:** `Assets/Localization/Tables/GameStrings_*.asset` do NOT contain the WO-1789 keys

### Glyph coverage fix (ru) — flagged by the combined-tree run, corrected

`GLYPH COVERAGE FAIL -- ru/dungeon.oilCaption missing U+0424`. **Confirmed at source, not taken
on faith:** the gate checks every scalar against the Static atlas
`Assets/Resources/Localization/Fonts/ElarionLocaleFallback.asset`
(`GlyphCoverageRegression.cs:70-88`). That atlas holds **201 glyphs, 62 of them Cyrillic**, and
**U+0424 (Ф) is absent while U+0444 (ф) is present** — the atlas was evidently built from the
characters the existing corpus actually used, and my caption was the only string in the whole ru
file to use a capital Ф. On device it would have rendered as tofu.

- **Was:** `МАСЛО ФОНАРЯ` (lantern oil) — needs U+0424.
- **Now:** `МАСЛО ЛАМПЫ` (lamp oil) — every glyph proven present in the atlas. Idiomatic Russian,
  keeps the all-caps caption style the other five gated locales use, and still says plainly that
  the bar is oil, which is the owner's actual requirement.
- Rejected alternative: lowercasing to `Масло фонаря` also dodges U+0424 but breaks the caption
  style. Also rejected: regenerating the font atlas via `LocaleFontBuilder` — that is a Unity
  editor bake this lane was told to hold, and rewording is the cheaper correct fix.

**Scope finding worth knowing:** only **en, es, pt-BR, de, fr, ru** are `enabledInBuild: true`, so
those are the only locales the glyph gate ever checks. `ar, ja, ko, zh-Hans` are
`ai-first-draft-internal-limited` and **not glyph-checked at all** — which is why a 201-glyph atlas
can pass despite the CJK/Arabic rows. Those four will need font work before they can be enabled;
that is pre-existing, not introduced here.

**Re-verified after the fix:** `GLYPH COVERAGE OK -- covers 184 scalar(s) across 6 enabled
locale(s)` for the ENTIRE corpus (not just my two keys), and `LOCALE_PARITY OK` again.

**Translations are AI first drafts and unreviewed by a native speaker** — same status as every
other non-base string in the project. One self-caught error worth recording: the Korean caption
first went in as 랜턱 (U+D131) instead of 랜턴 (U+D134); corrected in both mirrors.
