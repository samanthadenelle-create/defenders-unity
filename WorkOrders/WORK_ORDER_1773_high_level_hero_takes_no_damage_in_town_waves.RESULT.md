## 5. Design decisions a reviewer should check, each with its reason

**5.1 `wave.countCapPct` is NOT a dead knob — this was checked before registering it.** The risk was
real: `waves.json`'s authored `enemies[]` batches are INERT (`_RETIRED_batchFields`), and
`EndlessCountScale` feeds `CloneWaveWithScaledCounts`, which scales those dead batch counts. Had that
been its only consumer, the knob would have been the *"this dial does nothing yet"* trap WO-1763's
RESULT §9 had to clean up. `grep -n "EndlessCountScale"` returns **three** call sites, and the third is
`WaveManager.cs:2454` inside `SpawnSmartComposedWave` — the LIVE smart path, where the scale is applied
to each generated composition entry. So the knob reaches real bodies. **Registered on evidence, not on
the ticket's inference.**

**5.2 Identity is a SHORT-CIRCUIT in every case, not `value * 100 / 100f`.** Both consumers return the
caller's own float/int at identity. The oracle asserts **exact equality** (`!=`, not a tolerance) for
those cases on purpose — a tolerance would hide the very round-trip the short-circuit removes, and
"an empty table is today's town, bit for bit" stops being a provable sentence.

**5.3 The growth band start is READ off the curve, and guarded on the wrap mode.** `GrowthBandStart`
returns `int.MaxValue` ("never grow") for a null curve, an empty curve, or a curve whose `postWrapMode`
is not `Clamp`/`ClampForever`. A `Loop` or `PingPong` curve is already producing new values past its
last key, so adding a growth term would double-count. The time is `CeilToInt`-ed so a fractional
keyframe time cannot slip one wave of growth in before the clamp actually binds. **No consumer contains
the literal 20.**

**5.4 The recent-damage window WINS over the in-wave percent, and that ordering is a ruling.** A hero
being hit right now is in combat whatever a wave phase says — and the same `Update` runs in raid,
dungeon and overworld scenes that have **no `WaveManager` at all**. Pinned by case `[regen-gate]`.

**5.5 The FTUE carve-out is EXPLICIT rather than inferred.** WO-1773 §6 argues shape (ii) preserves the
1-HP recovery "naturally" because nothing is hitting the hero during the teaching beat. That is an
inference about a scripted beat, and CLAUDE.md §11B says an inference is not a proof — and the downside
if it is wrong is a NEW PLAYER permanently stuck at 1 HP with no recovery path. So
`TutorialFlow.HostilesSuppressedForTutorial` (the same predicate `HeroHealth.cs:845`'s own 1-HP floor
uses) returns FULL rate first and unconditionally. The oracle drives it with the harshest legal knobs.

**5.6 "Seconds since damage" is `+Infinity`, never 0, for a hero who has never been hit.** 0 would read
as "hit this very frame" and suppress town regen forever on a fresh save — a no-heal bug with no
on-screen symptom. `[regen-gate]` pins it.

**5.7 "Took damage" is recorded where HP ACTUALLY DROPS, after the whole mitigation chain.** A dodge, a
parry, a full talent block or a shield that erased the hit all `return` above that point, so none of
them arms the timer. Otherwise a fully-mitigating build would regen LESS than one that gets hurt.

**5.8 `TakeDamage`'s signature was NOT widened, and `ApplyContactDamage`'s was not either.** The
attacker is carried on a field set by the two entry paths: the melee tick names the primary of its
summed group (`"<name> +N more"`), and the interface path states plainly that it has **no attacker
reference** rather than reporting a stale melee attacker from an earlier tick — a plausible-looking lie
in a log is worse than "unknown".

**5.9 `RemoteTunables.Int` is never on a per-frame path.** It costs a spec lookup **and** a
`PlayerPrefs.GetInt`. So: `SafeZoneRecovery` caches the two ints behind a 6 s refresh, and
`WaveManager` folds the concurrency percent **once at `StartWave`** into `_maxSimultaneousFolded` — which
also means the cap cannot move underneath a wave already draining reinforcements against it, where
`live > cap` would read as a defect in the very trace that reports it. The two per-frame `WaitUntil`
predicates read the cached property.

**5.10 The concurrency fold honours BOTH zero traps.** An authored `0` means **UNCAPPED** to every read
site (each tests `> 0`), so `0` is handed back as `0` — scaling it would turn "no cap" into a finite one
with no row asking. And a real cap never rounds down to `0`, which would read as uncapped and release the
whole roster at once — the exact WO-1113 phone frame-rate cliff, reached by a dial meant to be safe.
Both pinned in `[count-folds]`, along with a check that the concurrency percent ceiling stays **tighter**
than the roster ceilings.

**5.11 `SpeedMultiplier` is deliberately NOT tunable.** Enemy move speed is a navigation and animation
property as much as a difficulty one: past a point it reads as a bug, outruns the hero's locomotion, and
fights the NavMeshAgent avoidance the concurrency cap exists to protect. If the owner wants it, it gets
its own knob and its own ceiling — not a share of the HP one. Written in-code so it is not read later as
an oversight.

**5.12 No number from `SafeZoneRecovery`, `WaveScalingCurve`, `WaveCompositionBuilder`, `waves.json` or
the scene is restated in any file this lane wrote.** Every baseline arrives as a parameter, and the
oracle supplies its own probe values. A literal copy would go red the first time the owner tuned the
content — and that is the same discipline WO-1763's §2.6 fix applied retroactively.

**5.13 An absolute ceiling exists on the effective strength multiplier (`x200`), and it is loud.** The
wave number is a genuinely **unbounded** input — `WaveManager.cs` records that `BestWave` is only floored
at 0 — so without a ceiling one typo produces enemies with more HP than a float usefully carries and a
wave that can never be cleared.

**5.14 `[identity]` asserts that wave 176 STILL EQUALS wave 60 at the shipping defaults.** That equality
is the reported defect, and pinning it is what proves the suite would notice if growth were ever switched
on by default — which would silently make every existing save harder with nobody asking.
