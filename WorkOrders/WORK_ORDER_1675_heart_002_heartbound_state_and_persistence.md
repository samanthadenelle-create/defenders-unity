## 0. Classification — **NEW model, but it lands beside an EXISTING one, and it must NOT go in the save**

### 0a. ⛔ THE SAVE IS CLIENT-AUTHORED. HEARTBOUND STATE CANNOT LIVE IN IT.

`api/game/save.js:70-72`, in the file's own words:

> `Sanity-check bounds (WO-120 §2 — soft currency stays client-owned, with server guards). Anti-grief / anti-corruption ceilings, NOT a server-authoritative economy`

and `:410-421`:

> `⛔ farming / raiding / dungeons / arena have NO per-action endpoint. They are simulated entirely on the client and reach this backend only inside the opaque save blob… It is a RECORD, NOT A CONTROL. Do not mistake it for enforcement.`

The whole snapshot is a JSONB blob the client writes (`api/schema.sql:59-84`, `game_state JSONB`). **Product rule 6 ("the backend is authoritative for game rewards") is therefore unsatisfiable by anything stored inside the save**, and HEART-004's *"a pulse can never pay the same player twice"* (spec `:449`) cannot be enforced by a field a replayed client blob can rewrite.

**Consequence, and it is the finding of this ticket:** `HeartboundState` is a **backend-owned Neon table**. The client holds, at most, a **read-only cached snapshot** for display.

### 0b. ⭐ **`SaveSchema.CurrentVersion` therefore DOES NOT BUMP.**

Read at source: `Assets/_Modules/Core/State/SaveSchema.cs:41` — `public const int CurrentVersion = 41;`. Migration pattern for reference: `Assets/_Modules/Core/State/SaveMigrator.cs:37` (the `SortedDictionary<int, Func<PersistedState,PersistedState>> Steps`), registration list `:76-82`, apply loop `:90-101`, worked example `MigrateToV41` `:780-812`, and the invariant stated repeatedly in the changelog — **SaveMigrator's top step must equal `SaveSchema.CurrentVersion`**.

**None of that is needed here, and that is the right answer, not a shortcut.** A bump would be the defect: it would put authoritative reward state on the client-owned wire. Record the decision in the RESULT so the next seat does not "fix" it by adding a field.

⚠ If a display-only cache *is* wanted client-side, `SaveMigrator.cs:50-61` documents that a purely additive nullable field needs **no `Steps` entry at all** — so even that costs no bump. Prefer PlayerPrefs (the `HeartfireService.cs:112-114` precedent) over the synced save, so a stale cache cannot round-trip to Neon and read as authority.

### 0c. ⚠ A stake→tier→rewards ladder **ALREADY EXISTS**, over the same wallet

`StakeRewardsResolver` (`Assets/_Modules/Core/Platform/StakeRewardsResolver.cs:152`) maps an active stake to a **tier** and a **cumulative reward list** from `Assets/Resources/Data/Canonical/stake-rewards.json` (path const `:155`, resolve `:205-235`). It has a shipped panel (`Assets/_Modules/Core/UI/StakeRewardsPanel.cs`), a VM (`Assets/_Modules/Core/UI/Mvvm/StakeRewardsVM.cs`), EditMode tests (`Assets/Tests/EditMode/StakeRewardsVMTests.cs`), a generated byte-exact fallback (`Assets/Editor/StakeRewardsFallbackGenerator.cs`) and a demo bootstrap (`Assets/_Modules/Core/Platform/StakeRewardsDemoBootstrap.cs`).

**HEART-002/003/006/008 build a SECOND ladder and a SECOND panel over the SAME input.** That is duplicated state by construction — the failure CLAUDE.md §2, §5, §8 and §16 each describe. See OWNER QUESTION Q-LADDER.

## 4. ⛔ OWNER QUESTIONS

### Q-WALLET. The spec's "Wallet Change" section presumes a player who OUTLIVES a wallet. This repo has no such player.
On the Seeker rail **the wallet IS the `player_id`** (`api/schema.sql:60`; `api/_lib/wallet-auth.js:129`, `:759-762`), and `api/_lib/wallet-auth.js:27-29` records the standing owner ruling: *"THE WALLET REMAINS THE SOLE IDENTITY ON THE SEEKER/APK ARTIFACT."* There is no linkage table (`grep -n "link" api/schema.sql` → only `social_links`, `:902`).

So spec `:241-246` — *"stops rewards from the old wallet / requires new verification / does not transfer the old wallet's effective staking weight / **retains lifetime cosmetic achievements** / starts a new continuous staking streak"* — is **four-fifths trivially true and one-fifth impossible**. A different wallet is a different player with a different save. Lifetime cosmetics cannot be retained because there is nothing to retain them on.

**The ruling needed:** (a) accept it — a wallet change is a new player, and the spec's section is deleted rather than implemented; or (b) build a player↔wallet linkage layer, which is a large new identity feature with its own account-takeover surface and is **not** in this spec. **This also rewrites HEART-010's "Wallet switching" scenario (WO-1683), which cannot be tested as written.**

### Q-LADDER. Two stake→tier ladders over one wallet: fold, or run both?
`stake-rewards.json` + `StakeRewardsResolver` + `StakeRewardsPanel` already do this (§0c). Heartbound's ten tiers (spec `:319-333`) are a second, richer ladder. **Options:** (a) Heartbound absorbs it — `stake-rewards.json` and its panel are retired and their cosmetic grants become Heartbound tier unlocks; (b) both ship, with a written note saying which is which and why a player sees two tier numbers for one stake; (c) `stake-rewards.json` becomes the *data source* for Heartbound's tier table (spec `:359` requires the thresholds be configuration-driven anyway). **Recommend (a) or (c).** (b) is the shape every stale-copy scar in CLAUDE.md started as.
