## 5. Design decisions a reviewer should check, each with its reason

1. **Identity is a SHORT-CIRCUIT, not `authored * 100 / 100f`.** At `pct == 100` the consumer returns
   the authored float itself. `1.3f * 100f / 100f` is not guaranteed bit-identical in single precision,
   and case `[identity]` asserts **exact** float equality on purpose — a tolerance there would hide the
   very round-trip the short-circuit removes. This is what makes "an empty table is today's raid, bit
   for bit" a provable sentence.
2. **The `> 0f` guard stays AHEAD of the resolve.** An authored `0` scaled by any percent is still `0`,
   and `FoldDifficulty` **no-ops at `<= 0`** — so a zero surviving into the resolve would read as
   "difficulty applied" while applying nothing. `ResolveFrom` re-states the guard at its own boundary
   too, and logs once when it fires. Case `[clamps]` pins both ends of this.
3. **The sentinel test comes BEFORE the offset clamp.** `-999` sits far below the `-5` floor
   deliberately; clamping first would silently turn "use the authored value" into "the easiest legal
   value" for every camp with no row at once. Pinned in `[offset-replace]` and again in `[clamps]`.
4. **`RaidGarrisonSpawner.FoldDifficulty` widened `private` → `public static`.** The `[folds]` case
   drives the **real** fold and the **real** `ApplyLevelScale` rather than re-implementing two
   multiplies in the oracle (an oracle that restates the code under test certifies only itself), and
   reflection is forbidden (CLAUDE.md §10). The reason is written in-code above the method so it is not
   read later as drift. It has no new call sites outside the oracle and is still static and stateless.
5. **`ResolveFrom(...)` takes the knob values as parameters**, and `Resolve(...)` reads them off the
   rail and calls it — the `RaidLootTunables.FractionFrom` / `Fraction` precedent. That is what lets
   `[folds]`, `[offset-replace]` and `[clamps]` drive every branch with **nothing loaded and no row
   written**.
6. **Camp ids are REUSED from `RaidLootTunables.CampIdCamp1..CampIdBastion`**, never re-declared. They
   are live, save-adjacent data with exactly one home.
7. **The oracle never asserts an authored baseline.** It reads each camp's authored multiplier and
   offset through `SceneConfigCatalog` at run time and asserts the **relationship** to the effective
   value. A literal would go red the first time the owner tuned a camp by hand — the opposite of
   useful — and would let the case certify a table that had moved.
8. **No number from `scene-configs.json` is restated in any file this lane wrote.** That is the same
   discipline as §2.6's fix, applied prospectively.
9. **A NEGATIVE row parses on every leg of the rail — verified at source, not assumed.** The sentinel
   and the legal `-5..-1` band would be a dead half-range if any parser rejected a leading sign, so all
   four were opened:
   - client wire value — `RemoteTunables.TryParseValue` (`:1817-1818`) ends in
     `int.TryParse(s, NumberStyles.Integer, InvariantCulture, out value)`; `NumberStyles.Integer`
     includes `AllowLeadingSign`. **Accepts.**
   - client local override — `ReadLocalOverride` (`:1786-1796`) uses `PlayerPrefs.GetInt`, which is
     signed. **Accepts.**
   - server write validator — `normalizeValue` (`api/_lib/tunables.js:347`) tests `/^-?\d{1,9}$/`.
     **Accepts**, and `-999` round-trips to `"-999"` (exercised by the manifest test's min/max
     round-trip assertion, which is green).
   - doc-parity oracle — `ParseDocTable` uses the same `NumberStyles.Integer` overload. **Accepts**,
     and the port in §3 read `-999` out of all four doc rows.
   So an explicit `-999` row is genuinely valid (it does **not** hit the `badvalue` Throttle), and the
   whole `-5..20` band is reachable. Nothing in the rail was widened to achieve this.
10. **`[offset-replace]`'s REPLACE-vs-ADD discrimination runs on SUPPLIED LITERALS (authored 4, row 2),
    not on the Bastion's authored offset** — and that is a deliberate hardening, not laziness. With an
    authored offset of **0**, REPLACE and ADD both yield the row value, so a catalog-derived probe
    could neither distinguish the two nor fail honestly: it would go red on correct code the day the
    owner authored a 0. That case asserts SEMANTICS, so literals are the honest input; the
    catalog-read half is kept for the sentinel fallback and the `baseEnemyLevel` floor, where the
    claim genuinely is about that camp's content. The floor block now also asserts the floor is a
    **floor and not a cap** (a hero well above `baseEnemyLevel` is still met at `playerLevel + offset`),
    because a cap there would make the offset knob do nothing for exactly the strong hero the felt
    report was about.
